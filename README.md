# LabFlow — умная очередь на сдачу лабораторных

Студент за минуту записывается в очередь и видит своё место и примерное время ожидания.
Преподаватель вызывает студентов, перетаскивает их в очереди, запускает тест и фиксирует результат.

## Возможности

**Студент**
- запись в очередь за 3 клика; выбранные лабы запоминаются;
- своё место, прогресс ожидания и время по часам («≈ 15 мин, около 10:45»);
- на главной — блок «Вы в очереди» с местом в каждой очереди;
- уведомления «Вы следующий» и «Вас вызвали!»: звук, вибрация, системное уведомление,
  мигающая вкладка (номер места виден прямо в заголовке вкладки);
- тест с таймером, прогрессом ответов и автоотправкой, когда время вышло;
- «Работа сдана ✓» с результатом теста, история и статистика в «Результатах».

**Преподаватель**
- живая очередь: перетаскивание, «Вызвать следующего» (клавиша <kbd>N</kbd>), <kbd>Esc</kbd>;
- таймер текущей сдачи с подсветкой, если студент сдаёт дольше плана;
- быстрые кнопки «Сдал / Не сдал» прямо в списке;
- прогноз: кто не успеет до конца пары;
- «Ссылка для записи» в один клик и **режим проектора** (`/board/:id`) для экрана в аудитории;
- статистика: итоги сдач, план/факт по длительности каждой лабы с советом, ведомость и
  выгрузка в **CSV** для Excel;
- «Через неделю» — создать такую же очередь на ту же пару; пресеты времени пар.

**Для всех**: светлая/тёмная/системная тема, адаптивный интерфейс (от 360 px, нижняя панель
вкладок на телефоне), уведомления о действиях, индикатор «нет интернета», страница 404.

## Быстрый старт

### Требования

- Python 3.12+;
- Node.js 24 с npm (версия проекта указана в `.nvmrc`; при использовании nvm выполните `nvm use`);
- Docker с Compose для локальной PostgreSQL 16. Со своей БД Docker не нужен.

Все команды ниже выполняются из корня репозитория.

### Первый запуск

```bash
./dev.sh --seed
```

Скрипт создаст `backend/.env` из примера, установит зависимости, поднимет PostgreSQL,
применит миграции, добавит демо-данные и запустит backend и frontend. После сообщения
о готовности откройте сайт http://localhost:5173 или Swagger http://localhost:8000/docs.
Docker автоматически выберет свободный локальный порт для PostgreSQL, а скрипт
подключит к нему backend. Порт можно посмотреть командой `docker compose port db 5432`.
Если демо-данные не нужны, запустите `./dev.sh` без флага.

| Роль | Логин | Пароль |
| --- | --- | --- |
| Преподаватель | `teacher` | `1234` |
| Студент | `student` | `1234` |
| Администратор | `admin` | `1234` |

Эти пароли используются только в локальной разработке. Повторный запуск с `--seed`
обновляет пароли демо-аккаунтов.

### Ежедневная работа

```bash
./dev.sh
```

Скрипт повторно использует установленные зависимости, пока не изменятся файлы
зависимостей, применяет новые миграции и запускает серверы с автоматическим
обновлением кода. `Ctrl+C` останавливает оба сервера. Если скрипт сам запустил
PostgreSQL, он остановит и её. Заранее запущенная БД продолжит работать, в том
числе для подключений из IDE. Данные сохраняются в Docker volume.

Для своего PostgreSQL задайте `DATABASE_URL` в `backend/.env` и запустите
`./dev.sh --external-db`. В этом режиме Docker не используется.
Другой порт сайта: `FRONT_PORT=5174 ./dev.sh`.

### Проверки перед PR

На чистой машине `./dev.sh --setup` устанавливает зависимости обеих частей.
Для этой команды достаточно Python и Node.js с npm. Её можно выполнять и при
занятых портах. Если вы уже запускали `./dev.sh`, зависимости установлены.

У каждой части есть отдельные команды установки и проверки.

```bash
./dev.sh --setup frontend    # нужен Node.js с npm
./check.sh frontend          # типы по backend/openapi.json, линтер, тесты и сборка

./dev.sh --setup backend     # нужен Python
./check.sh backend           # линтер, форматирование, типы, SQLite и проверка OpenAPI
```

Перед PR выберите полную проверку на SQLite или PostgreSQL.

```bash
./check.sh             # обе части, тесты backend на SQLite
./check.sh --postgres  # обе части, тесты и миграции на отдельной PostgreSQL
```

Оба режима проверяют линтеры, форматирование, типы, тесты frontend, сборку и
актуальность OpenAPI и типов API. Проверка не перезаписывает файлы схем.
Режим `--postgres` запускает сервис `db` из общего `docker-compose.yml` в отдельном
Compose-проекте с собственным томом и свободным портом. Скрипт создаёт в нём базу
`labflow_test` и после проверки удаляет тестовый контейнер, том и сеть. Для проверки одного backend
на PostgreSQL выполните `./check.sh backend --postgres`. CI также проверяет backend
на PostgreSQL.

### Частые проблемы

| Сообщение или ситуация | Что сделать |
| --- | --- |
| Нужен Node.js 24 | Выполнить `nvm use` или установить Node.js 24 и открыть новый терминал. |
| Docker не запущен или недоступен | Запустить Docker; со своей БД использовать `--external-db`. |
| Порт 5432 занят | `./dev.sh` выберет другой порт PostgreSQL автоматически; если запуск всё равно не удался, проверить `docker compose ps db`. |
| Порт 8000 или 5173 занят | Остановить сервер на этом порту; для frontend можно задать `FRONT_PORT`. |
| Не удалось применить миграции | Проверить `DATABASE_URL` в `backend/.env`; для Docker также проверить `docker compose ps db`. |
| `./check.sh` не находит зависимости | Выполнить `./dev.sh --setup` или установить выбранную часть через `./dev.sh --setup frontend` / `./dev.sh --setup backend`. |

### Другие способы запуска

После первого запуска можно открыть серверы в двух терминалах отдельно.
Сначала поднимите БД из корня репозитория:

```bash
docker compose up -d --wait db
DB_PORT="$(docker compose port db 5432 | cut -d: -f2)"
cd backend && DATABASE_URL="postgresql+asyncpg://labflow:labflow@127.0.0.1:$DB_PORT/labflow" .venv/bin/uvicorn app.main:app --reload
```

```bash
cd frontend && npm run dev
```

Когда закончите, остановите серверы через `Ctrl+C`, затем выполните
`docker compose stop db` из корня репозитория.

Весь стек можно запустить в Docker: `docker compose up --build`. Сайт будет на
http://localhost:8080; изменения кода потребуют пересборки образов. Демо-данные
для этого режима создаются отдельно командой `docker compose exec backend python -m app.seed`.

### Изменение API

После изменения эндпоинтов обновите схемы:

```bash
cd backend && .venv/bin/python -m app.export_openapi openapi.json
cd ../frontend && npm run gen:api
```

`./check.sh` и CI сообщат, если схемы устарели.

## Как устроено

- `backend/app/services/queue_engine.py` — алгоритм очереди (чистые функции):
  `key = D − k·W`, сортировка по возрастанию, закреплённые места, время ожидания.
  Через `D/k` минут ожидания запись обгоняет любую новую — бесконечного ожидания нет.
- `backend/app/services/queue_service.py` — загрузка из БД, пересчёт и рассылка по WebSocket.
- `backend/app/ws/` — `WS /api/v1/ws/queues/{id}?token=…`; пересчёт по таймеру раз в минуту.
- `frontend/src/hooks/useQueueState.ts` — WebSocket с автопереподключением;
  пока соединения нет, опрос раз в 5 секунд.
- Закреплённый преподавателем студент продвигается вместе с очередью: когда кто-то выше
  уходит, его место уменьшается на 1.

## Выкладка на Render (бесплатно)

Всё работает как **один веб-сервис**: сервер FastAPI отдаёт и собранный сайт, и API, и WebSocket
с одного адреса. Описание — в [render.yaml](render.yaml), сборка — в [Dockerfile](Dockerfile).

1. Залейте репозиторий на GitHub.
2. На [render.com](https://render.com) войдите через GitHub → **New → Blueprint** → выберите репозиторий.
3. Render покажет базу `labflow-db` и сервис `labflow` и спросит пароли демо-аккаунтов
   `SEED_ADMIN_PASSWORD`, `SEED_TEACHER_PASSWORD`, `SEED_STUDENT_PASSWORD`
   (пустой пароль — аккаунт не создаётся). Нажмите **Apply**.
4. После сборки сайт откроется по адресу вида `https://labflow-xxxx.onrender.com`.

По [условиям бесплатного тарифа Render](https://render.com/docs/free), веб-сервис засыпает
после 15 минут без входящего HTTP-трафика и сообщений WebSocket; первое открытие после
этого занимает около минуты. Бесплатная PostgreSQL истекает через 30 дней, а ещё через
14 дней данные удаляются; встроенных бэкапов у неё нет. Для длительного хранения нужна
другая постоянная БД: адрес задаётся переменной `DATABASE_URL`.

В `render.yaml` путь `/ready` проверяет соединение с БД. Render начнёт новую выкладку
после успешного завершения проверок CI для ветки `main`.

### Мониторинг после выкладки

- `/health` отвечает, когда работает процесс приложения; `/ready` дополнительно
  проверяет БД и возвращает 503 при недоступности базы.
- После появления публичного адреса задайте в GitHub Actions переменную репозитория
  `LABFLOW_URL`, например `https://labflow-xxxx.onrender.com` (без `/ready`).
- [.github/workflows/monitor.yml](.github/workflows/monitor.yml) раз в час проверяет
  `/ready`. При сбое workflow создаёт одну открытую задачу в GitHub Issues и закрывает
  её после восстановления. Запланированные проверки начнутся после попадания файла
  в основную ветку; пока `LABFLOW_URL` не задан, проверка пропускается.

В GitHub должны быть включены Actions и Issues. Запланированные запуски могут
задерживаться; [GitHub также отключает их в публичном репозитории после 60 дней без
активности](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows).
